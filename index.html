Reviewing a Business Term
for Publication

Three checks a Data Steward should perform
before approving or rejecting a proposed term

Introduce the three quality gates: wording clarity, ontological fit, and data linkage.
Check 1 of 3

Wording & Clarity

What to look for

Can a non-expert understand this?

  • Read the description as if you had no domain background. Does it make sense without additional context?
  • Identify technical jargon that is not defined elsewhere in the glossary — each undefined term is a potential rejection reason.
  • Check whether alternative names / synonyms are provided and whether they are commonly used across business units.
  • Verify that the definition uses complete, grammatically correct sentences and does not rely on abbreviations without expansion.
  • A good description answers: What is it? What is it not? How is it measured or expressed?

Tip: paste the description into a prompt and ask a general-audience LLM to explain it back to you — if it struggles, reviewers will too.

Example

Term proposed: Cap Rate

❌ Weak description

"The cap rate used in RE valuation models for NOI discounting."

  • Uses unexpanded abbreviations: RE, NOI
  • Assumes reader knows "valuation models" means DCF analysis
  • No alternative wordings; no unit mentioned (percentage? decimal?)

✔ Improved description

"Capitalisation Rate (Cap Rate): the ratio of a property's annual Net Operating Income (NOI) to its current market value, expressed as a percentage. Used to estimate the expected return on a real-estate investment."

  • Abbreviations expanded on first use
  • Alternative name listed: Capitalisation Rate
  • Unit stated: percentage
Focus on the reader's perspective. The approver is often not the domain expert — if the description requires specialist knowledge to parse, it should be sent back for amendment.
Check 2 of 3

Ontological Fit & Conflicts

What to look for

Does the term belong in its category?

  • Treat the assigned category as a node in an ontology. Ask: Is this term a specialisation of the category concept, or does it belong somewhere else?
  • Use the upcoming context service to surface related terms and parent/sibling concepts for the assigned category.
  • Scan for near-duplicates already published in the same category — different names for the same concept create ambiguity in downstream systems (e.g. Client Id vs Customer Number).
  • Check for clashes: terms in the same category whose definitions overlap significantly but are given different names without a clear distinction.
  • If overlap exists, decide: merge, alias, or disambiguate with a scope qualifier (e.g. Customer Number (CRM) vs Customer Number (ERP)).

Tip: a context-service query on the category can return the 5–10 most semantically similar existing terms — review these before approving.

Example

Category: Party Identifiers

Existing published terms in this category:

  • Customer Number — "Unique numeric identifier assigned to a customer in the CRM system."
  • Counterparty ID — "Identifier for external trading counterparties."

New term proposed: Client Id

⚠ Potential conflict

  • Definition reads: "The ID of a client as stored in core banking."
  • "Client" ≈ "Customer" in common usage — different source system, but same real-world concept?
  • Action: request submitter to clarify whether this is a distinct concept or an alias for Customer Number scoped to core banking.

✔ Resolution options

  • Add as alias: Client Id → synonym of Customer Number
  • Publish as scoped variant: Customer Number (Core Banking)
The context service (semantic search over the glossary) is the key tool here. Even without it, a manual scan of the target category for similar terms is essential.
Check 3 of 3

Linkage to Existing Data

What to look for

Where does this term live in the data landscape?

  • Identify the databases, tables, and columns that carry the values described by this term. Without at least one known data location, the term floats unanchored — hard to adopt in practice.
  • Check whether those columns are already tagged with a different business term — that reveals existing naming conflicts or redundant terms at the data level.
  • Verify data type and format consistency: if the term says "expressed as a percentage", do the mapped columns store 0.05 or 5? Discrepancies must be documented.
  • Look for columns with similar names across multiple schemas — these may be the same concept stored differently, which supports the case for a shared business term.
  • If no data mapping exists yet, note it as a gap and flag for the submitter to supply at least one reference source.

Tip: a data-lineage or metadata search query on the term name (and its synonyms) across catalogued sources is the fastest starting point.

Example

Term: Net Operating Income

Metadata search results:

Database Table Column Type
re_core property_financials noi_annual DECIMAL(18,2)
risk_dw asset_valuation net_op_income FLOAT
reporting kpi_summary NOI VARCHAR(20)

⚠ Issues to flag

  • reporting.kpi_summary.NOI stores the value as VARCHAR — inconsistent with the other two numeric columns; possible formatted string.
  • Two different column names (noi_annual, net_op_income) already exist — the new term should document both as known source-column mappings.
Data mapping transforms a glossary from a documentation exercise into something operationally useful. Encourage submitters to supply at least one source reference.

Reviewing a Data Class Definition
for Publication

Four checks a Data Steward should perform
before approving or rejecting a proposed data class

Data classes classify existing data by column name and format — examples include Global Location Number (GLN) and Germany's Steuernummer. Their checks differ from business terms: no category hierarchy, but strict requirements on uniqueness, fingerprint, data-quality rules, and sensitivity.

Data classes describe how to identify a type of data value in the wild — by its name pattern and format signature. The four checks here replace the ontology-category checks used for business terms and add fingerprint and sensitivity dimensions.
Check 1 of 4

Uniqueness

What to look for

Is the name truly unique across all data classes?

  • Data classes have no category hierarchy — unlike business terms, a data class is not disambiguated by its parent category. The name alone must be globally unique.
  • Search the full data-class registry for exact matches and near-matches (e.g. Steuernummer vs Tax Number (DE) vs German Tax ID).
  • Check whether the proposed class is a regional variant of an already-published global class. If a global Tax Identification Number exists, a narrower Steuernummer may be valid only if it genuinely adds specificity.
  • Verify that synonyms and alternative names listed in the definition do not clash with the primary name of an existing data class.
  • A data class name should be self-contained: anyone seeing GLN in a column header should map it to exactly one data class, no qualifier needed.

Tip: run a search on both the full name and common abbreviations before approving.

Example

Proposed data class: GLN

Existing data classes in the registry:

  • Global Location Number — 13-digit GS1 identifier for physical locations.
  • GS1 Location Code — alias for the same GS1 standard.

⚠ Potential clash

  • GLN is the common abbreviation of Global Location Number — registering it as a separate data class creates ambiguity.
  • Action: add GLN as a synonym/alias of Global Location Number rather than creating a new entry.

✔ Resolution

  • Keep Global Location Number as the canonical name.
  • Add GLN, GS1 Location Code as registered synonyms.
The absence of a category hierarchy is what makes uniqueness the first check for data classes. Without it, two data classes with overlapping names or abbreviations will cause matching ambiguity in automated column classifiers.
Check 2 of 4

Fingerprint

What to look for

Can a classifier reliably recognise values of this data class?

  • A fingerprint is a matching rule that lets automated tools identify columns likely to carry values of this data class — either by column name pattern or by value format.
  • Accepted fingerprint forms:
    • Regex: a regular expression that matches valid values (e.g. ^\d{3}/\d{3}/\d{5}$ for a Steuernummer).
    • Natural language rule: a precise descriptive rule for cases where a pure regex is insufficient (e.g. "13 numeric digits, first digit non-zero, passes GS1 check-digit algorithm").
  • The fingerprint must be specific enough to avoid false positives — a regex that matches any 10-digit number will hit phone numbers, account IDs, and postal codes alike.
  • If both a column-name pattern and a value-format pattern are available, prefer the value-format pattern — it is more robust across systems with non-standard column naming.
  • Test the fingerprint against at least two known positive examples and one known negative example before approving.

Tip: if a regex cannot be written without significant false-positive risk, a natural-language rule is acceptable — but must be precise enough for a human or LLM to apply consistently.

Example

Data class: Steuernummer

❌ Weak fingerprint

"Consists of digits and slashes."

  • Too vague — matches phone numbers, fractions, date strings
  • No length constraint; no structural rule

✔ Precise fingerprint

Regex: ^\d{2,3}/\d{3}/\d{5}$

  • Format: 123/456/78901 — 2–3 digits, slash, 3 digits, slash, 5 digits
  • Matches known positive: 123/456/78901 ✓
  • Rejects known negative: +49-30-123456 ✗ (phone number)

Complementary column-name pattern: column name contains steuer, steuernr, or tax_id (German locale).

The fingerprint is the machine-readable contract for automated classification. A vague fingerprint leads to noisy results; an overly tight one misses valid values. Both a regex and a natural-language fallback are acceptable as long as the rule is testable.
Check 3 of 4

Data Quality Rules

What to look for

How do we spot violations of this data class?

  • Data quality rules are the flip side of the fingerprint: where the fingerprint defines what a valid value looks like, quality rules define what a violation looks like — and how severe it is.
  • At minimum, a data class submission should include:
    • Format violation rule: values that fail the fingerprint regex or pattern (e.g. wrong digit count, missing separators).
    • Completeness rule: whether null/empty values are permitted or constitute a violation.
    • Uniqueness rule: is each value expected to be unique within a dataset, or can it repeat?
  • Optional but recommended: a referential rule — does the value need to resolve against a reference registry (e.g. the GS1 GLN database)?
  • Quality rules should be expressed in testable, tool-agnostic language so they can be implemented in any data-quality framework.

Tip: link quality rules to a severity level (Critical / Major / Minor) so downstream data-quality dashboards can prioritise remediation.

Example

Data class: Global Location Number (GLN)

Rule Condition Severity
Format Not 13 numeric digits Critical
Check digit Fails GS1 Mod-10 check Critical
Completeness NULL or empty string Major
Uniqueness Duplicate within dataset Major
Referential Not found in GS1 registry Minor

Format and check-digit rules can be automated immediately; registry lookup requires connectivity to the GS1 service — flag as a future enhancement if not available.

Data quality rules operationalise the data class. Without them the class is purely descriptive — you cannot measure conformance or drive remediation. Even two or three testable rules are significantly better than none.
Check 4 of 4

Sensitivity & PII Likelihood

What to look for

How likely is this data class to carry PII or sensitive data?

  • Data classes are often used by automated scanners to classify columns at scale. A high-sensitivity rating signals that any column matched to this class should be reviewed for privacy and regulatory compliance.
  • Rate sensitivity on a three-point scale:
    • High — directly identifies an individual or entity (e.g. national ID numbers, biometric markers).
    • Medium — can identify individuals when combined with other data (quasi-identifiers such as postal code + birth date).
    • Low — describes assets, products, or locations with no direct link to natural persons.
  • Note: IKC (Information Knowledge Catalog) does not currently expose a dedicated PII marker on data classes — sensitivity must be documented in the description field and enforced through governance policies.
  • Check whether applicable regulations apply (GDPR, CCPA, etc.) and whether a data-protection impact assessment is required before the class can be published.
  • If the class is High sensitivity, ensure the description explicitly names the legal basis for processing and any retention constraints.

Tip: any data class whose fingerprint can match a government-issued ID number, financial account number, or biometric value should default to High sensitivity.

Example

Sensitivity rating comparison

Data Class Rating Reason
Steuernummer High Directly identifies a German natural person or business
Postal Code (DE) Medium Quasi-identifier — combines with other fields to narrow identity
Global Location Number Low Identifies physical locations (warehouses, stores) — not persons

⚠ Current IKC limitation

  • No dedicated PII marker field in IKC data class definitions.
  • Workaround: include a structured sensitivity statement in the description, e.g.:
    «Sensitivity: High — personal data under GDPR Art. 4(1). Retention: 10 years post-contract.»
Sensitivity drives downstream access controls, masking policies, and regulatory obligations. Even if IKC does not enforce it structurally, documenting it in the description ensures data engineers and privacy officers can discover and act on it.

Out of scope (first stage)

Known limitations & future work

  • Columnar scope only: Data classes can refer to columns. Broader/narrower scope (dataset-level, record-level) is deferred.
  • Java / JavaScript type rules: Data classes can specify matching rules for Java classes or JS types — needs further investigation before inclusion.
  • PII marker: IKC does not currently expose a dedicated PII marker on data classes. Use the description field as a workaround; formal marker support is a future platform enhancement.

Set the stage: the problem is a sprawling legacy glossary with 1,000+ terms accumulated over years — many overlapping, poorly defined, or misclassified. The five-phase roadmap collapses these into a lean, authoritative set and prevents the problem from recurring.
Phase 1 of 5

Inventory & Assessment

Steps

Profile the current state of the glossary

  • Extract all terms: Export every business term, definition, owner, and metadata tag into a unified staging area — a single flat view of what exists.
  • Profile data quality: Identify completely empty definitions, missing steward assignments, and formatting inconsistencies (mixed casing, punctuation styles, stray HTML).
  • Baseline count: Record the raw term count per domain/category so you can measure reduction progress across the following phases.

Tip: export to a spreadsheet or database table so every subsequent phase can annotate the same rows with status flags (KEEP, MERGE, RETIRE).

Example

Glossary snapshot — Customer domain

Term Owner Definition Flag
Customer ID CRM Team Unique identifier for a customer. OK
Client_ID — (empty) No owner, no def
Cust. Number Finance Customer number in ERP. Possible dup

Raw count, Customer domain: 347 terms

Quality flags at this stage: 42 empty definitions · 61 missing owners · 18 formatting issues

The goal here is visibility, not decisions. Avoid the temptation to start merging in Phase 1 — just get a complete, annotated export so later phases can work systematically.
Phase 2 of 5

Hybrid Deduplication & Semantic Clustering

Steps

Collapse duplicates at scale — without reviewing every pair

  • Fast Filtering: Pre-screen terms into broad candidate pools (by category, first token, or n-gram hash) so comparisons happen only within plausible clusters — not across all 1,000+ pairs.
  • Lexical Similarity: Flag naming variations, typos, and convention mismatches (e.g. Client ID vs Client_ID vs ClientId).
  • Semantic AI Matching: Use embedding-based similarity to surface conceptually identical terms with different names (e.g. Vendor ≈ Supplier).
  • Smart Grouping: Form synonym-candidate clusters without forcing rigid rules — let the model propose groupings for human review.
  • Streamlined Review: Auto-merge high-confidence duplicates; route borderline cases to Data Stewards. Confirmed duplicates become a canonical preferred term + synonym aliases.

Target: reduce the raw term count by 40–70 % before touching definitions.

Example — cluster discovered by AI

Synonym cluster: Vendor

Term Sim. Decision
Vendor — ✔ Canonical term
Supplier 0.94 ✔ Auto-merged → alias
External Provider 0.81 ⚑ Route to steward
Third-Party Seller 0.76 ⚑ Route to steward

Result: 4 terms → 1 canonical + 1 alias + 2 for human review

Across all clusters, 347 Customer-domain terms reduced to ~130 after Phase 2.

The key insight is pre-screening into pools. Comparing 1,000 terms pairwise = 500,000 comparisons; comparing within 50 pools of 20 terms = 9,500 — a 98 % reduction. Semantic embeddings then catch the conceptual duplicates that lexical matching misses.
Phase 3 of 5

Clarity & Definition Standardisation

Steps

Make every surviving term business-readable

  • Apply standard templates: Enforce an ISO 11179-style structure — a definition must state what the term is, not just how it is used. Include: concept type, distinguishing characteristics, units or format.
  • Automate quality checks: Flag definitions that are too short (< 10 words), circular ("Client ID is the ID of a client"), or contain unexpanded acronyms.
  • Assign domain experts: Route flagged terms to the relevant Data Steward or SME for rapid rewriting — batch by domain to minimise back-and-forth.

Tip: run automated checks in a CI-like pipeline so no term can advance to Phase 4 until it passes all quality gates.

Example — definition rewrite

Term: Vendor (canonical)

❌ Before (circular, no context)

"Vendor ID is the ID used to identify a vendor."

  • Circular: defines the term with itself
  • No type information (numeric? alphanumeric?)
  • No scope (which system issues the ID?)

✔ After (ISO 11179-style)

"A legal entity or individual that supplies goods or services to the organisation under a contractual agreement. Identified by a unique alphanumeric Vendor ID assigned at contract registration. Synonyms: Supplier, External Provider."

  • States what a vendor is (concept type + distinguishing property)
  • Mentions identifier format and lifecycle event
  • Captures synonyms surfaced in Phase 2
ISO 11179 is the international standard for metadata registries. Even a lightweight version — concept type + key property + unit/format — dramatically improves downstream usability. Automated checks remove the burden of manual triage from stewards.
Phase 4 of 5

Ontological Alignment

Steps

Fit the cleaned terms into the target structure

  • Map to top-level concepts: Assign each business term to a core ontological class (e.g. Customer Account maps to the class Financial Account).
  • Define relationships: Establish semantic links using predicate logic — isA, partOf, hasProperty — to make the ontology machine-traversable.
  • Validate logic: Run a semantic reasoner to detect contradictions — e.g. a term classified both as a Person and an Organisation — before loading into the production catalog.

Tip: validate in a sandbox ontology first. Logical contradictions are much cheaper to fix before the terms are published and linked to data assets.

Example — relationship mapping

Terms mapped in the Party ontology class

Term Class Predicate
Vendor Party isA LegalEntity
Vendor ID Identifier hasProperty Vendor
Purchase Order Agreement partOf Vendor

⚠ Reasoner flag caught during validation

  • Contractor was classified as both Person and Organisation — contradiction resolved by splitting into Individual Contractor and Contractor Company.
Ontological alignment turns a flat list of terms into a graph — making it possible for catalog tools, search engines, and AI assistants to traverse and reason over the glossary rather than just keyword-matching it.
Phase 5 of 5

Governance & Load — Lock the Gate

Steps

Transition to production and prevent future drift

  • Conduct a final review: Use a governed workflow to obtain formal sign-off from business stakeholders before any term goes live.
  • Load into target system: Migrate the canonical terms into your data catalog or ontology management tool, preserving synonym mappings and relationship links from Phase 4.
  • Lock the gate: Enforce strict validation rules on new term creation — no new term is published without passing the three quality gates (wording, ontology fit, data linkage) and receiving at least one steward approval.

The gate is only as strong as its enforcement. Automating the approval workflow removes the bottleneck and ensures every new term is evaluated consistently.
